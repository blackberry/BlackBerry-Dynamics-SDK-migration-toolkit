# Task: Generate Migration Report

## Goal

Produce a machine-readable `migration-report.json` inside
`dynamics-migration-tool/output/`. It summarizes what the migration changed,
what's covered, and what still needs manual attention.

**This prompt runs AFTER the required migration prompts are complete (`00pre`, `00`, `01`–`09`, including `05a/05b/05c`) and after applicable prompt `11` (secure push) and prompt `03c` (Background Authorize intent capture). Prompt `00b` (architecture diagrams) is optional and is not a prerequisite for report generation.**

This prompt has a **hard gate** (step 9) that cross-checks the execution
plan in `migration-analysis.json` against the executed-prompts audit in
`bootstrap.json`. If any applicable domain is missing both an executed
prompt and a developer deferral, the report is **NOT** written and the
prompt aborts with a remediation message. Applicable domains can no
longer be silently downgraded to `manualTodos`.

---

## Steps

### 0. Load Analysis, Bootstrap, and Module Map Artifacts (Required)

Read `dynamics-migration-tool/output/migration-analysis.json` generated by
Prompt 00 and use it as the source artifact for:
- domain applicability/tier values
- the binding `executionPlan`
- `egressFeatures[]` feature inventory
- unsupported feature candidates
- manual TODO candidate seeding

Read `dynamics-migration-tool/output/migration-plan-state.json` generated by
the migration prompts and use it as the source artifact for:
- `dispositions[]` call-site closure state
- `egressFeatureDecisions[]` final feature-level egress outcomes
- `safDecision` objects that must be expanded into `safFindings[]`

Read `dynamics-migration-tool/output/bootstrap.json` generated by
Prompt 00pre and use it as the source artifact for:
- `executedPrompts` — full execution audit
- `deferredDomains` — domains the developer chose to defer
- `runId` — stable run identifier that must be copied into the report
- `catalogVersion` — baseline catalog contract version for drift checks
- `provenance` — bootstrap-level git / SDK / toolkit audit fields
- `uem.gdApplicationId` and `uem.gdApplicationVersion` — must match
  the bootstrap-driven `settings.json` file(s) under
  `${primary_assets_dirs}` (see module-map context below)
- `toolkit.version` — for cross-validation against the report's
  toolkit block

Read `dynamics-migration-tool/output/module-map.json` generated by
Prompt 00pre and use it as the source artifact for:
- `primaryAppModule` — the module migrated this run. Populate the
  report's required `targetModule` block from it and the module-map
  top-level discovery fields:
  - `name` ← `primaryAppModule.name`
  - `path` ← `primaryAppModule.path`
  - `appliesAndroidApplicationPlugin` ← `true`
  - `applicationId` ← `primaryAppModule.applicationId`
  - `buildFile` ← `primaryAppModule.buildFile`
  - `buildFileType` ← `primaryAppModule.buildFileType`
  - `conventionPluginRef` ← `primaryAppModule.conventionPluginRef`
  - `discoveryMethod` ← `module-map.json.discoveryMethod`
  - `projectShape` ← `module-map.json.projectShape`
  - `sourceSetCount` ← length of `primaryAppModule.sourceSets[]`
  - `inScopeLibraryModules` ← `libraryModulesInScope[]` entries
  - `otherAppModules` ← `otherAppModules[]` entries
- `libraryModulesInScope[]` — every library module included in
  source-level audits this run.
- `excludedTestOnlyModules[]` — modules deliberately skipped because
  they only ship test code; surface this list in the report so
  reviewers know the scope was bounded.
- `otherAppModules[]` — sibling application modules that were NOT
  migrated this run (multi-application projects). Surface this list
  with a note that each requires its own migration run if
  enterprise coverage is required.
- `conventionPlugins[]` — Kotlin convention plugin source files
  that compose the primary module's Android configuration. Surface
  the list so reviewers can trace where Gradle edits actually
  landed (`compileSdk`/`minSdk` may live in a convention plugin
  rather than the module's own build file).
- `${primary_assets_dirs}` — every settings.json target written by
  prompt 02; the UEM cross-check below validates each.
- `${in_scope_main_src}` — every primary + library `src/main/java`
  / `src/main/kotlin` directory; all source-level scans below
  iterate this set.
- `${in_scope_res_dirs}` — every primary + library resource directory;
  FileProvider path resources, menus, layouts, and WebView/share UI may
  live outside the primary module.
- `${in_scope_manifests}` — every primary + library manifest; provider,
  service, receiver, and intent-filter cleanup checks iterate this set.

Read `dynamics-migration-tool/contracts/api-catalog.v1.0.0.json` and use
it as the allowlist for `apisReplaced[].catalogRow` values (step 2).

If any of the three analysis files is missing, STOP and re-run the
corresponding prompt (`00-analyze-app.md` or `00pre-bootstrap.md`).
If the API catalog is missing, STOP and report that
`contracts/api-catalog.v1.0.0.json` must be present for report
generation.

### 1. Inventory All Changes

Scan the project for every `[BB_DYNAMICS-MIGRATION]` comment. The
search must cover every in-scope module (primary + libraries) plus
every Gradle file across the module map and `conventionPlugins[]`,
not just `app/`:

```bash
# ${in_scope_modules} expands to space-separated module paths from
# module-map.json (primaryAppModule + libraryModulesInScope[]). Pass
# them as roots to rg so the audit reaches library modules.
rg "\[BB_DYNAMICS-MIGRATION\]" -g "*.java" -g "*.kt" \
  -g "*.xml" -g "*.gradle" -g "*.gradle.kts" -n \
  ${in_scope_modules}

# Also scan convention plugin source files separately — they live
# outside any application/library module path.
rg "\[BB_DYNAMICS-MIGRATION\]" -n ${convention_plugin_files}
```

For each hit, record:
- File path (relative to project root)
- Owning Gradle module — `primaryAppModule.name` for paths under the
  primary module's tree, the matching `libraryModulesInScope[*].name`
  for paths under a library module, or `"<convention-plugin>"` for
  paths inside a convention plugin source file. This becomes
  `apisReplaced[*].modules[]` per the v2.1.0 schema.
- Whether the file was modified, created, or deleted
- One-line description of the change

After tallying, populate `summary.migrationCommentCountByModule` —
an object keyed by module path with the per-module count of
`[BB_DYNAMICS-MIGRATION]` audit comments. The aggregate
`summary.migrationCommentCount` must equal the sum of the
per-module counts.

Confirm that no unknown audit tag variants appear in source. The only
valid tag is `[BB_DYNAMICS-MIGRATION]`. The following command must
return zero matches:

```bash
rg "\[BB_DYNAMICS-WAIVER:" -g "*.java" -g "*.kt" \
  -g "*.xml" -g "*.gradle" -g "*.gradle.kts" -n
```

If it returns any match, abort report generation and tell the developer
to either (a) complete the migration of those call sites to Dynamics
APIs, or (b) defer the entire owning domain in
`bootstrap.json deferredDomains[]`. The toolkit does not support
line-level exceptions.

### 2. Catalog API Replacements with Risk, Catalog Evidence, and Snippets

Read `dynamics-migration-tool/contracts/api-catalog.v1.0.0.json` and use
it as the allowlist for all API replacements.

For each Dynamics API introduced, record:
- **catalogRow** (REQUIRED) — the stable row `id` from
  `contracts/api-catalog.v1.0.0.json` that authorizes this replacement.
  Every `apisReplaced[]` entry MUST reference a valid catalog row. If no
  catalog row exists for a replacement, do NOT include it in
  `apisReplaced[]` — add a `manualTodo` instead and note the missing
  catalog entry. Free-text API provenance is not a substitute.
- Category (networking, storage-file, storage-sql, ui-widget, clipboard, policy, webview, icc, auth, gradle)
- Original API (fully qualified class name)
- Replacement API (fully qualified class name)
- Files where the replacement was made
- Total occurrence count
- Risk level and reason:
  - low: drop-in replacement, same method signatures
  - medium: API shape changes, requires refactoring but equivalent behavior
  - high: behavioral change that could cause runtime issues
- Before/after code snippets:
  - Pick the clearest example from the codebase (1-5 lines each)
  - Escape quotes and backslashes for valid JSON

**Catalog cross-check**: After assembling all `apisReplaced[]` entries,
verify that every `catalogRow` value matches a `rows[].id` in
`contracts/api-catalog.v1.0.0.json`. Also verify that the catalog row's
`supportStatus` is `"supported"` — rows with `"unsupported"` or
`"needs-review"` must not appear as completed replacements (use
`manualTodos` instead).

### 3. Assess Coverage

For each migration area, determine status:
- migrated: all instances replaced, no standard APIs remain
- partial: some instances replaced, some remain
- not-applicable: the app does not use this category

**Required JSON shape — coverage values are objects, NOT bare strings.**
The downstream toolkit-analysis report and the `validate.sh` report
contract both require this dict shape per area:

```json
"coverage": {
  "secureNetworking":   { "status": "migrated",       "details": "OkHttp interceptor wired; HttpURLConnection replaced." },
  "securePush":         { "status": "not-applicable", "details": "No FirebaseMessagingService handlers or Dynamics Push Channel usage were detected." },
  "backgroundAuthorize": { "status": "not-applicable", "details": "No background entry points were detected in bootstrap.processModel.backgroundEntryPoints[]." },
  "secureFileStorage":  { "status": "migrated",       "details": "All Context.openFile* and java.io.FileInput/OutputStream call sites routed through GDFileSystem." },
  "secureSql":          { "status": "migrated",       "details": "SupportSQLiteOpenHelper.Factory bridges Room to com.good.gd.database.sqlite.SQLiteOpenHelper." },
  "secureUiWidgets":    { "status": "not-applicable", "details": "No covered standard/AppCompat/Material text or search widgets were detected in app-controlled UI." },
  "secureClipboard":    { "status": "not-applicable", "details": "No platform or Jetpack Compose clipboard usage detected." },
  "authorization":      { "status": "migrated",       "details": "GDStateListener implemented on Application; activityInit() called from launch Activity onCreate." },
  "policyManagement":   { "status": "not-applicable", "details": "App does not consume RestrictionsManager." },
  "webview":            { "status": "not-applicable", "details": "App does not embed WebView." },
  "icc":                { "status": "not-applicable", "details": "App does not register ICC intent filters." }
}
```

A bare string value (e.g. `"secureNetworking": "migrated"`) will FAIL
the validator's report-contract check and FAIL the toolkit-analysis
report's coverage roll-up (every area would be classified as
`unknown`). Always emit `{ "status": "...", "details": "..." }`.

Areas to assess (use these exact keys):
- `secureNetworking` (HTTP, Socket, OkHttp)
- `securePush` (FCM hardening + Dynamics Push Channel)
- `backgroundAuthorize` (per-candidate Background Authorize intent and app-side wiring)
- `secureFileStorage`
- `secureSql`
- `secureUiWidgets`
- `secureClipboard` (DLP-enforced copy/paste — platform **and** Jetpack Compose)
- `authorization` (initialization + GDStateListener)
- `policyManagement`
- `webview`
- `icc` (secure sharing)

### 4. Collect Manual TODOs

List anything the agent could not automate:
- UEM entitlement configuration
- Runtime testing with UEM server
- Credential and activation testing
- Third-party library compatibility verification
- External rollback copy when `bootstrap.json.backup.branch` and
  `backup.createdFromCommit` are both `null` (this is the supported
  non-git bootstrap path; tell the developer to preserve a project copy
  outside the migration workspace before accepting the output)
- External / secondary storage data leakage risks (see below)
- Any items flagged during earlier prompts

Each `manualTodos[]` entry must use the unified manual-intervention shape:
`id`, `title`, `domain`, `blocking`, `owner: "applicationDeveloper"`,
`severity`, `reason`, `affectedModules[]`, `evidence[]`,
`requiredActions[]`, `acceptanceCriteria[]`, and
`status: "open" | "completed" | "acceptedRisk" | "notApplicable"`.
`severity` must be exactly `P0|P1|P2|P3` — do **not** emit analysis-era
`priority` (`blocker|high|medium|low`). If a draft still has
`priority: "P0"`…`"P3"`, `prepare-report-artifacts.py` aliases it to
`severity` and drops `priority`; other priority vocab fails the report
contract with an explicit hint.
Set `blocking: true` only when the item must prevent `go`; otherwise set
`blocking: false` and keep it visible as a non-blocking manual intervention.

**Opaque native/closed-source findings (MANDATORY when applicable):**
- If final validation warns about prebuilt `jniLibs/**/*.so`, JNI
  `System.loadLibrary(...)` without in-repo native source, or opaque local
  binary SDK dependencies (`.aar`/`.jar`, `fileTree`, `flatDir`), you MUST add
  developer-owned non-blocking `manualTodos[]` entries (`blocking: false`).
- Include owning module(s), concrete evidence (for example library file names,
  dependency declarations, source paths), and proof actions (vendor
  attestation, source audit, runtime filesystem/network monitoring, replacement,
  or explicit acceptance).
- Explicitly state that these internals are **out of automatic migration scope**
  unless evidence shows an overlapping non-waivable rule violation; only then
  escalate that specific TODO to `blocking: true`.

**Broad DLP/export findings (MANDATORY when applicable):**
- If final validation warns about any broad DLP/output surfaces (sensitive
  notifications, printing, screenshots/recent thumbnails, autofill,
  accessibility, IME/keyboard, external browser/custom tabs, rich clipboard URI
  content, drag/drop), you MUST add matching developer-owned `manualTodos[]`.
- Default every such TODO to `blocking: false` and make the manual ownership
  explicit (`owner: "applicationDeveloper"`), with affected modules, evidence,
  and concrete follow-up actions.
- Escalate to `blocking: true` only when the same path overlaps an existing
  non-waivable rule (for example `externalStorage` security-blocker surfaces or
  unapproved outbound sharing). Do not mark these broad DLP findings as
  blocking without overlap evidence.

When a TODO represents unresolved engineering work that the developer may
want to continue with a future AI session, add an optional `followUp`
object:

- `whyBlocked` — why the toolkit could not safely finish it
- `safeNextOptions[]` — safe directions the developer can choose from
- `suggestedAgentPrompt` — copy/paste-ready follow-up prompt text
- `evidenceFiles[]` — optional project-root-relative files/artifacts to
  inspect first

**Compose clipboard manual findings (MANDATORY when applicable):**
- If prompt 09 left any unmanaged Compose clipboard API (`LocalClipboardManager`,
  `LocalClipboard`, Compose `setClipEntry` / `getClipEntry`, or Compose
  `ClipboardManager` / `Clipboard` for app-controlled copy/paste), add a
  non-blocking `manualTodos[]` entry per call site or file cluster with:
  - explicit remediation (copy `GDClipboardAdapter`, rewire to
    `setPlainText` / `getPlainText`, or remove the feature), and
  - `coverage.secureClipboard.status` = `partial` (never `migrated` or
    `not-applicable` while unmanaged Compose clipboard remains).
- Record migrated Compose clipboard in `apisReplaced[]` with
  `catalogRow` `clipboard-compose-001` … `clipboard-compose-003` and
  category `clipboard`.

**Compose ICC chooser manual findings (MANDATORY when applicable):**
- If prompt 08 left View-system ICC chooser wiring in Compose-first screens
  (`MaterialAlertDialogBuilder`, `AlertDialog.Builder`, or
  `showShareChooser(` invoked from `@Composable` code), add a non-blocking
  `manualTodos[]` entry per file cluster with remediation to copy
  `GDICCProviderShareDialog` and rewire provider selection.
- Set `coverage.icc.status` = `partial` (never `migrated` or
  `not-applicable` while unmanaged Compose ICC chooser patterns remain).
- Record migrated Compose ICC chooser work in `apisReplaced[]` with
  `catalogRow` `icc-compose-001` or `icc-compose-002` and category `icc`.

**FileProvider residual-surface findings (MANDATORY when applicable):**
- Re-scan `${in_scope_main_src}` + `${in_scope_manifests}` + `${in_scope_res_dirs}`
  for `FileProvider.getUriForFile`, `androidx.core.content.FileProvider`,
  `android.support.FILE_PROVIDER_PATHS`, and path tags in
  `res/xml/file_paths.xml` (or equivalent provider path resources).
- If `FileProvider.getUriForFile` call sites are gone but provider declaration or
  path resources remain, add a **blocking** security item (do not bury as generic
  warning):
  - append a `releaseReadiness.blockingItems[]` entry prefixed
    `[DLP-BLOCKER][icc/fileprovider-stale-manifest]`, and
  - add a `manualTodos[]` entry with `blocking: true` describing required
    removal/cleanup before production.
- If FileProvider is intentionally retained for a non-sharing path, add an explicit
  `manualTodos[]` entry (`blocking: true` if any sensitive risk)
  documenting all of:
  - why FileProvider is still needed,
  - which path tags it exposes (`files-path`, `cache-path`, etc.),
  - whether those paths can contain sensitive/container data,
  - why the retained surface is safe under the Dynamics DLP contract.
- If retained paths include `external-path`, `external-files-path`,
  `external-cache-path`, or `root-path`, treat as hard-blocking security posture
  until manually justified + remediated.

**Blocked SAF decision TODOs (MANDATORY when applicable):**
- Read `dynamics-migration-tool/output/migration-plan-state.json`.
- For every `dispositions[]` entry with a `safDecision` object:
  - Create a corresponding `safFindings[]` report entry. Do not parse
    arbitrary `note` prose as the source of truth.
  - If `safDecision.migrationDecision` is
    `BLOCKED_PENDING_DEVELOPER_APPROVAL` or `MANUAL_REDESIGN_REQUIRED`,
    add a `manualTodos[]` entry with `blocking: true` describing
    the disabled/removed user-visible feature and the product decision
    still needed.
  - If `safDecision.migrationDecision` is
    `ALLOW_WITH_DLP_ENFORCEMENT`, require
    `runtimeDlpEnforced: true`, `developerDecision:
    "ALLOW_WITH_DLP_ENFORCEMENT"`, and a non-empty decision timestamp
    or developer rationale. Missing structured approval keeps
    `releaseReadiness.recommendation = "no-go"`.
- A safely blocked SAF export can satisfy security closure, but pending
  product decision keeps release readiness `no-go` until the developer
  explicitly accepts permanent blocking or chooses a replacement.

**Egress capability outcomes (MANDATORY when applicable):**
- Read `migration-analysis.json` `egressFeatures[]` and
  `migration-plan-state.json` `egressFeatureDecisions[]`.
- For every analyzed egress feature, create a corresponding top-level
  `egressFeatures[]` report entry. Do not collapse these into generic
  prose-only `manualTodos`.
- Keep outcome parity: when a feature has a
  `migration-plan-state.json egressFeatureDecisions[]` row, report
  `egressFeatures[].outcome` must match that decision exactly.
- Status mapping is deterministic:
  - `REMOVE` or `REPLACE_WITH_DYNAMICS` -> `implemented`
  - `MANUAL_INTERVENTION_REQUIRED` -> `manual-follow-up`
  - `BLOCKED_UNTIL_APPROVED` -> `blocked`
- Each report entry should include:
  - `id`
  - `featureName`
  - `domain`
  - `outcome` (`REMOVE`, `REPLACE_WITH_DYNAMICS`,
    `MANUAL_INTERVENTION_REQUIRED`, `BLOCKED_UNTIL_APPROVED`)
  - `status` (`implemented`, `manual-follow-up`, or `blocked`)
  - `reason`
  - `migrationAction`
  - `userVisibleChange`
  - `secureAlternative`
  - `sourceFiles[]`
  - `followUp` when outcome is `MANUAL_INTERVENTION_REQUIRED` or
    `BLOCKED_UNTIL_APPROVED`
- `REMOVE` entries must explain what UI/implementation/supporting surface was
  removed.
- `REPLACE_WITH_DYNAMICS` entries must name the approved Dynamics boundary
  actually used (for example ICC/AppKinetics or secure clipboard).
- `BLOCKED_UNTIL_APPROVED` entries must state that the original Android path
  is disabled and unreachable today, and why the capability remains blocked.
- `MANUAL_INTERVENTION_REQUIRED` entries must explain why the kit did not
  preserve the original Android path and what safe next options remain.
- When an entry is `BLOCKED_UNTIL_APPROVED` or
  `MANUAL_INTERVENTION_REQUIRED`, add a matching `manualTodos[]` item unless
  an equivalent SAF/manual item already exists.
- **How the report-contract gate decides a todo "matches" a feature
  (MANDATORY — this is a deterministic string match, not a semantic one):**
  the gate concatenates each `manualTodos[]` entry's
  `id`, `title`, `reason`, `evidence[]`, `requiredActions[]`, and
  `acceptanceCriteria[]` into one lowercased blob, and treats the todo as
  matching only if the egress feature's `id` **or** `featureName` appears as a
  substring of that blob. A prose todo that describes the same feature but
  never names its `id` or `featureName` will **fail** the gate. Put the exact
  egress feature `id` (for example `egress-save-saf-dir-001`) verbatim into the
  matching todo's `evidence[]` or `requiredActions[]`.
- **`BLOCKED_UNTIL_APPROVED` egress features force a blocking todo and a
  `no-go` release (MANDATORY):** at least one matching `manualTodos[]` entry
  must have `blocking: true`. Do not default these to `blocking: false` on the
  grounds that they are "just pending a product decision" — a disabled
  user-visible capability is release-blocking until the developer approves a
  Dynamics-safe redesign or accepts permanent removal. Because any
  `blocking: true` todo forces `releaseReadiness.recommendation` to `no-go`
  (blocking manual interventions cannot coexist with `go`/`go-with-risks`),
  every `BLOCKED_UNTIL_APPROVED` egress feature makes the overall
  recommendation `no-go`.

**Build failure classification**: For any build failures recorded during
migration, clearly distinguish:
- **Migration-caused**: introduced by the tool's changes (must be resolved)
- **Pre-existing**: already present before migration according to developer attestation/history (report, don't block)
- **Unrelated**: environment-specific or transient issues

Include pre-existing blockers in `manualTodos` with `reason: "pre-existing"`.

### 4c. Capture Runtime-Only Failures Discovered After Static Pass

If migration defects are discovered during runtime testing (while static
validation is green), record them in `runtimeFailures[]` in the report.

Each entry MUST include (enforced by the v2.1.0 schema and `validate.sh`):
- `id` — stable identifier, e.g. `RF-1`
- `category` — one of `startupAuthSequencing`, `deferredInitNullability`,
  `duplicateActivityInit`, or `other` (use `other` only when none of the
  enumerated categories applies, and explain the symptom in `rootCause`)
- `symptom` — runtime behavior / log signature
- `rootCause` — why static checks missed it
- `promptGap` — which prompt contract failed to force this check
- `validatorGap` — which validator phase/check did not catch it
- `fix` — generic remediation pattern (link to a Pattern in
  `steering/21-authorization-deferral-patterns.md` when applicable)
- `status` — `open` or `fixed`

When any of the enumerated categories is observed in runtime logs / device
testing, the report MUST contain at least one `runtimeFailures[]` entry of
that `category`. Include the key log signature in `symptom` and note in
`rootCause` whether the issue reproduced on the first-launch pre-auth
flow.

Category quick-reference (see `steering/81-migration-report-contract.md`
for the canonical table):

- `startupAuthSequencing` — secure API work executes before authorization
  (e.g. `GDNotAuthorizedError` from `RoomTrackingLiveData` on
  `arch_disk_io`). Validator: `[AUTH-DB-001]`. Fix: Pattern 2 + 12.
- `deferredInitNullability` — first-launch NPE from delayed model fields
  / `!!` in `onViewCreated` / `setupObserver`, or incomplete deferred-init
  state machine wiring. Validator: `[AUTH-UI-001]`, `[AUTH-UI-002]`,
  `[AUTH-UI-003]`. Fix: Pattern 12.
- Cold-start `Activity.onResume` / `onPause` / `onCreateOptionsMenu` NPE or
  `UninitializedPropertyAccessException` on fields created only in
  `initializeAuthorizedUi` / `setupNavigation` / `runOnAuthorized`.
  Validator: `[AUTH-UI-004]`. Fix: Pattern 14 (ready/`isInitialized`
  lifecycle **and menu** guards, Phase-2 nav-before-observe order,
  `invalidateOptionsMenu()` after auth).
- `duplicateActivityInit` — duplicate `activityInit(this)` calls in an
  Activity inheritance chain (e.g. `GD Monitor Fragment already inserted`).
  Validator: `[AUTH-INIT-001]`. Fix: keep `activityInit` in the base class
  only OR the subclass only — never both.

**External Storage Data Leakage**: Any feature that writes sensitive data
outside the Dynamics secure container (external storage, SD card, MediaStore,
shared directories, FileProvider sharing to non-Dynamics apps) MUST be listed
as a manual TODO with `blocking: true`. These features create data exfiltration
risks because data outside the container is unencrypted, accessible to other
apps, included in device backups, and not wiped on remote wipe. The developer
must decide post-migration whether to remove, redirect to the secure container,
route through ICC, or file an explicit time-bound deferral (`deferredDomains`)
with owner and expiry.

### 4d. Media / Export Containment Section (MANDATORY when applicable)

If the migration touched camera, gallery, MediaStore, `MediaRecorder`,
capture intents, output URIs, or file/media export behavior, populate a
dedicated top-level `mediaContainment` object in `migration-report.json`.

`mediaContainment.summary` must explain:

- whether app-owned media now remains inside the Dynamics container,
- whether a managed in-container gallery replaced public Gallery /
  MediaStore behavior,
- whether any controlled explicit export remains,
- and whether any native media writer or output-URI limitation still
  requires manual intervention / no-go.

For every media/file write path, add a `mediaContainment.mediaWritePaths[]`
entry with:

- `sourceFile`
- `api`
- `originalBehavior`
- `migratedBehavior`
- `staysInContainer`
- `usesDirectSecureStream`
- `usesFilesystemStaging`
- `publicExportRemains`
- `manualInterventionRequired`
- `followUp` when the path still uses filesystem staging, leaves public
  export, or requires manual intervention

For every export/share/capture-intent path, add a
`mediaContainment.exportPaths[]` entry with:

- `sourceFile`
- `pattern`
- `status` (`disabled | migrated | controlled | unresolved`)
- `dlpImpact`
- `behaviorChange`
- `safeOutcome` (`safe | partial | no-go`)
- `followUp` when the path is still unresolved or not fully safe. Use the
  same shape as above: `whyBlocked`, `safeNextOptions[]`,
  `suggestedAgentPrompt`, optional `evidenceFiles[]`

Do not hide camera/media containment changes only inside generic
`manualTodos` prose.

Native OS gallery/viewer launches for secure media
(`Intent.ACTION_VIEW`, `MediaStore.ACTION_REVIEW`,
`Intent.CATEGORY_APP_GALLERY`) do **not** qualify as `controlled`
export. If such a path remains for secure-container-owned media, record
it as `status: "unresolved"` with `safeOutcome: "no-go"` unless it was
replaced by an in-app secure viewer/gallery or Dynamics ICC.

### 5. Identify Unsupported Features

List any app features or third-party libraries that are incompatible with
Dynamics, along with the reason and any workaround. Include features that
write to external/secondary storage if they fundamentally conflict with
Dynamics DLP policy (e.g., "export all data to SD card").

**CRITICAL: Verify workarounds before listing.** Before adding a
third-party library incompatibility to `unsupportedFeatures`, search the
codebase for an existing workaround implementation. Common patterns:

```bash
# Check if byte[] loading workaround exists for image libraries
rg "load\(bytes|load\(byteArray|readAllBytes|toByteArray" -g "*.java" -g "*.kt" -n ${in_scope_main_src}
# Check for safe non-filesystem workarounds. Native copyToTemp/createTempFile
# remains unsafe and must not be counted as a resolved limitation.
rg "toByteArray|ByteArrayOutputStream|MemoryFile|ParcelFileDescriptor\.createPipe|com\.good\.gd\.file\.FileOutputStream|com\.good\.gd\.file\.FileInputStream" \
  -g "*.java" -g "*.kt" -n ${in_scope_main_src}
# Check if OutputStream workaround exists for CameraX
rg "OutputFileOptions.Builder.*OutputStream|openForWrite" -g "*.java" -g "*.kt" -n ${in_scope_main_src}
```

Classification rules:
- **Unresolved limitation** (list in `unsupportedFeatures`): No code
  workaround exists in the codebase. The `workaround` field should
  describe the recommended approach.
- **Resolved limitation** (do NOT list in `unsupportedFeatures`): A code
  workaround is already implemented and is one of: bounded in-memory
  conversion, GD-backed secure temporary storage, direct Dynamics streams,
  or a pipe/memory descriptor fed by Dynamics streams. Instead, document
  the workaround in the relevant `apisReplaced` entry for that category
  (e.g., add a note in the `riskReason` or `after` snippet showing the
  workaround pattern).
- **Still unresolved / blocker**: native `copyToTemp`, `createTempFile`,
  `tempFile`, app-private `cacheDir`/`filesDir` staging, or
  write-temp-then-copy patterns. These are plaintext workarounds, not
  secure resolution.

Only genuinely unresolved incompatibilities belong in `unsupportedFeatures`.
Listing already-implemented workarounds as "unsupported" misrepresents the
migration state and creates false action items.

For each `unsupportedFeatures[]` entry, include a `followUp` object with:

- `whyBlocked`
- `safeNextOptions[]`
- `suggestedAgentPrompt`

## 12. Validation Runs Via the Recorder

When the prompt-10 record call below is invoked,
`record-prompt-execution.sh` first runs deterministic artifact normalization
(same helper as step 11a), then runs a split final gate and refuses to write
the `executedPrompts[]` entry unless **both** gates pass:

1. **Source gate**  
   `validate.sh --mode final-source --prompt 10`  
   Writes `dynamics-migration-tool/output/.last-source-check.json`
   (and mirrors latest run to `.last-check.json`).
2. **Report-contract gate**  
   `validate.sh --mode report --prompt 10`  
   Writes `dynamics-migration-tool/output/.last-report-check.json`
   (and mirrors latest run to `.last-check.json`).

On success, the recorder appends prompt 10 to `bootstrap.json`
`executedPrompts[]`, then **owns provenance refresh** for
`migration-report.json` by calling `sync-report-provenance.py` with both
sidecars. The sync step copies bootstrap provenance and sets report
validation from **source gate truth** (`.last-source-check.json`):
`validation.*` and `blockingFailuresFromValidate`. Report-contract outcomes
must not overwrite migrated-app security fields.

**Do not manually edit report `provenance` or validation fields** after a
successful record call — that duplicates recorder logic and reintroduces
`validate.sh` failures. Only patch those fields when diagnosing a toolkit
defect (then file a maintainer fix); otherwise fix the underlying migration
artifacts and re-invoke the recorder.

If the recorder reports a validation failure:

1. Read gate-specific violations from:
   - `output/.last-source-check.json` for source gate failures
   - `output/.last-report-check.json` for report-contract failures
2. Rewrite `migration-report.json` / `Dynamics_Migration_Readme.md` (or fix
   underlying source for source-gate failures) using
   full-file overwrite (never patch-based tools — see "File Write Method"
   above).
3. Re-invoke the recorder. It re-runs both gates, syncs bootstrap
   provenance into the report after the `executedPrompts[]` append, and
   exits non-zero if provenance still does not match bootstrap.

If the recorder/validator exits with code `3`, treat it as a hard retry-budget
escalation:

1. Stop re-running prompt 10 source/report gates in a tight loop.
2. Read `output/migration-loop-state.json` and `output/.last-source-check.json`
   or `output/.last-report-check.json` for the repeated signature.
3. Route remediation back to the owning prompt/domain (for example 05c for
   secure-file findings, 08 for ICC, 09 for secure UI/clipboard), then rerun
   prompt 10 only after targeted checks stabilize.

If the recorder reports missing migration-plan dispositions, an
open `requires[]` gate, or any other state gap, fix the underlying
state first, refresh all report artifacts (`migration-report.json`,
`Dynamics_Migration_Readme.md` if affected), and
then re-invoke the recorder. Do not leave a report generated from the
pre-remediation state.

This write→record→fix loop replaces the older single-sidecar full-sweep
flow that could leave stale report validation facts.

  `domain<TAB>surface<TAB>count<TAB>message`) if present. The file is
  written by `tooling/validate.sh` `security_blocker()` during phase
  scans and is the source of truth for findings that violate the
  Dynamics secure-container contract (today: `externalStorage/*` rows from
  Phase 4 external-storage API scans and Phase 8b FileProvider path-surface
  scans). For each row in the log:
  - copy the message verbatim into `releaseReadiness.blockingItems[]`,
    prefixed with `[SECURITY-BLOCKER][<domain>/<surface>]`;
  - add a `manualTodos[]` entry with `blocking: true`, a
    `title` that begins
    `"Manual intervention required before production use — "` and
    summarises the surface, and a `reason` that names the secure
    Dynamics replacement to apply (see catalog rows
    `fs-java-ext-001 .. fs-java-ext-005` in
    `contracts/api-catalog.v1.0.0.json`);
  - if the report schema is at v2.1.0 or later, populate the optional
    top-level `securityBlockers[]` array with one object per row
    (`{ "domain", "surface", "count", "message", "remediation",
    "catalogRows" }`).
  When the log is non-empty:
  - `releaseReadiness.recommendation` MUST be `"no-go"` (never
    `"go-with-risks"` or `"go"`);
  - `summary.overallStatus` MUST be `"failed"` (never `"complete"` or
    `"partial"`);
  - `migrationConfidence.level` MUST be `"low"` and the `rationale`
    MUST name "security blocker" / "external storage" explicitly;
  - `coverage.secureFileStorage.status` MUST be `"partial"` whenever any
    `externalStorage/*` blocker remains. Do NOT leave
    `coverage.secureFileStorage.status = "migrated"` while MediaStore,
    SAF, FileProvider, raw-path, or other container-boundary escape
    findings are still open;
  - any remaining capture-intent output URI flow, public Gallery restore,
    or native media-writer filesystem staging must appear in
    `mediaContainment` and keep the migration partial / no-go;
  - `securityPosture.dataAtRest.status` MUST be `"partial"` (or
    `"unverified"` if the writer count is large) and its `summary`
    MUST state that residual external-storage call-sites mean
    enterprise data can leave the Dynamics container, it is not
    encrypted, not included in remote wipe, and not covered by DLP;
  - the `validation` block MUST reflect a failed run (do NOT mark
    `validation.passed: true` while security blockers exist).
- **Do NOT** describe an unmigrated external-storage call-site as
  "intentional export boundary, deferred" or use any language that
  implies developer sign-off can waive the finding. Deferral of
  `externalStorage` is rejected by Phase 0; the only way for an
  external-storage call-site to leave the report green is migration
  or removal of the call-site. A `manualTodos[]` entry with
  `blocking: true` is the report's record of "still open";
  it is not a waiver. (This rule exists because earlier toolkit
  versions let MediaStore / external-storage writes ship under a
  "deferred with developer sign-off" label — that path is closed.)
