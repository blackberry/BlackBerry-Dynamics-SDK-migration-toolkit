# Steering: Authorization Deferral Patterns (Lessons from Real Migrations)

This file documents generalized patterns for deferring secure API access
until the Dynamics container is authorized. These patterns were discovered
through real migration experience and address the most common class of
runtime crashes in migrated apps.

---

## The Core Problem

Swapping imports (e.g., `android.database.sqlite` → `com.good.gd.database.sqlite`)
is the easy part of migration. The hard part is that every call site that
touches a secure API must be deferred until `onAuthorized()` fires. In a
real app, secure API access is scattered across:

- Activity `onCreate()` methods
- ViewModel `init {}` blocks
- Fragment `onViewCreated()` methods
- App widget factories and providers
- BroadcastReceivers (alarms, reminders)
- Data migration / schema upgrade routines
- Lazy-initialized singletons
- Utility functions called during early initialization

Simply moving code from `onCreate()` to `onAuthorized()` in the main
Activity is not enough. The authorization state must propagate to every
component that touches secure APIs.

**If the Architecture Diagrams exist** (generated by Prompt 00b at
`dynamics-migration-tool/output/architecture-diagrams.md`), consult them
before applying patterns. Specifically:
- Section 4A (Full Startup Chain Trace) shows every call chain from
  lifecycle event to secure API
- Section 4B (Summary Table) maps each chain to a deferral pattern
- Section 5 (Secure API Call Graph) provides bottom-up reverse traces
  that catch chains top-down tracing misses
- Section 7 (Migration Risk Heatmap) prioritizes which components to fix first

This eliminates the need to re-discover the dependency graph during
implementation.

## Pattern 1: Observable Authorization State

`20-auth-initialization.md` defines the Application class with a static
`isContainerAuthorized` flag and a one-shot `runOnAuthorized(Runnable)`
callback. For apps using reactive patterns (LiveData, Flow, RxJava),
**add** an observable `authorized` field to that same class:

```kotlin
// Add to the Application class defined in 20-auth-initialization.md
val authorized = MutableLiveData(false)

override fun onAuthorized() {
    isContainerAuthorized = true
    authorized.postValue(true)
    // ... existing runOnAuthorized callback logic from steering/20
}
```

This gives two complementary mechanisms — use both:

| Mechanism | Use Case |
|-----------|----------|
| `isContainerAuthorized` (static boolean) | Synchronous guards in BroadcastReceivers, utility functions, widget providers (Patterns 4, 5, 7) |
| `authorized` (LiveData) | Lifecycle-aware observation in ViewModels, Fragments, Activities (Patterns 2, 3, 5, 6) |

## Pattern 2: Deferring ViewModel Initialization

### The Problem

ViewModels commonly initialize database connections and start observing
LiveData queries in their `init {}` block. In a standard Android app this
is fine because the database is always available. After migration to
Dynamics secure SQLite, the `init {}` block runs before the container is
authorized, causing `GDNotAuthorizedError`.

### The Pattern

Observe the Application's `authorized` LiveData in the ViewModel's `init`
block. When it emits `true`, initialize the database and start observing:

```kotlin
class MyViewModel(private val app: Application) : AndroidViewModel(app) {

    private lateinit var database: MyDatabase
    // Fields that depend on database — initially null
    var items: LiveData<List<Item>>? = null

    // Signals to Fragments that database fields are ready to observe
    val databaseReady = MutableLiveData(false)

    init {
        val myApp = app as MyApplication
        myApp.authorized.observeForever(object : Observer<Boolean> {
            override fun onChanged(value: Boolean) {
                if (value) {
                    myApp.authorized.removeObserver(this)
                    initDatabase()
                }
            }
        })
    }

    private fun initDatabase() {
        database = MyDatabase.getDatabase(app)
        items = database.myDao().getAllItems()
        // Signal that database-dependent fields are now safe to access
        databaseReady.postValue(true)
    }
}
```

### Key Points

- Use `observeForever` because ViewModels have no lifecycle owner.
- Remove the observer after first `true` to avoid re-initialization.
- Expose a `databaseReady` signal so Fragments know when it is safe to
  call methods that access database-backed fields.
- Fields that depend on the database should be nullable or `lateinit`
  until initialization completes.

## Pattern 3: Deferring Fragment Data Observation

### The Problem

Fragments typically call methods in `onViewCreated()` that access
ViewModel fields backed by database LiveData. If the ViewModel's database
fields are not yet initialized (because authorization has not happened),
these calls throw NullPointerException or GDNotAuthorizedError.

### The Pattern

Observe the ViewModel's `databaseReady` signal before setting up data
observers:

```kotlin
abstract class MyFragment : Fragment() {

    private val viewModel: MyViewModel by activityViewModels()
    private var observerSetUp = false

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        setupUI()  // Safe — no data access

        // Defer data observation until database is ready
        if (viewModel.databaseReady.value == true) {
            observerSetUp = true
            setupDataObserver()
        } else {
            viewModel.databaseReady.observe(viewLifecycleOwner) { ready ->
                if (ready && !observerSetUp) {
                    observerSetUp = true
                    setupDataObserver()
                }
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        observerSetUp = false  // Reset for fragment recreation
    }

    private fun setupDataObserver() {
        getObservable().observe(viewLifecycleOwner) { list ->
            adapter.submitList(list)
        }
    }

    abstract fun getObservable(): LiveData<List<Item>>
}
```

### Key Points

- The `observerSetUp` flag prevents double-setup if `databaseReady` emits
  `true` multiple times or if the fragment is recreated.
- Reset the flag in `onDestroyView()` so it works correctly on fragment
  recreation.
- Check `databaseReady.value` first for the fast path (already authorized).
- Use `viewLifecycleOwner` (not `this`) for fragment LiveData observation.

### Concrete Java Fragment Example (from a real migration)

The following example is drawn directly from a migrated gallery Fragment.
It illustrates precisely which code is safe to run pre-authorization versus
what must be deferred.

```java
public class GalleryFragment extends Fragment {

    private RecyclerView photoGrid;
    private GalleryAdapter adapter;
    private PhotoDao photoDao;
    private MediaRepository mediaRepository;
    private LiveData<List<PhotoEntity>> currentLiveData;

    // [BB_DYNAMICS-MIGRATION] Guard flag: prevents double-init if authorized fires
    // more than once (e.g. after lock/unlock cycle)
    private boolean dependenciesInitialized = false;

    @Override
    public void onViewCreated(@NonNull View view, @Nullable Bundle savedInstanceState) {
        super.onViewCreated(view, savedInstanceState);

        // [OK] SAFE pre-authorization: pure view setup, no secure API access
        photoGrid = view.findViewById(R.id.photo_grid);
        photoGrid.setLayoutManager(new GridLayoutManager(requireContext(), 2));
        adapter = new GalleryAdapter("thumbs", this);  // constructor only, no I/O
        photoGrid.setAdapter(adapter);
        setupFilterTabs();       // adds tab labels, pure UI
        setupSelectionToolbar(); // wires menu item listeners, pure UI

        // [BB_DYNAMICS-MIGRATION] Defer Room DB init and LiveData observation until
        // after the Dynamics container is authorized. Do NOT move this into onCreate()
        // or call AppDatabase.getInstance() above this block.
        MyApplication.getAuthorized().observe(getViewLifecycleOwner(), isAuthorized -> {
            if (Boolean.TRUE.equals(isAuthorized) && !dependenciesInitialized) {
                initDependencies();       // ← opens Room DB (requires authorized container)
                dependenciesInitialized = true;
                observePhotos();          // ← starts LiveData query (requires authorized container)
            }
        });
    }

    @Override
    public void onResume() {
        super.onResume();
        // [BB_DYNAMICS-MIGRATION] Guard: only observe if dependencies are initialized.
        // Without this guard, onResume() would call observePhotos() before onAuthorized()
        // fires on a cold start, crashing with GDNotAuthorizedError.
        if (dependenciesInitialized) {
            observePhotos();
        }
    }

    @Override
    public void onHiddenChanged(boolean hidden) {
        super.onHiddenChanged(hidden);
        // [BB_DYNAMICS-MIGRATION] Same guard as onResume() — fragment may become visible
        // before authorization completes.
        if (!hidden && dependenciesInitialized) {
            observePhotos();
        }
    }

    private void initDependencies() {
        // [NOT OK] Would crash here before onAuthorized() — GDNotAuthorizedError
        AppDatabase db = AppDatabase.getInstance(requireContext());
        photoDao = db.photoDao();
        mediaRepository = new LocalEncryptedMediaRepository(
                new AndroidInternalEncryptedFileStore(requireContext()),
                photoDao);
    }

    private void observePhotos() {
        if (currentLiveData != null) {
            currentLiveData.removeObservers(getViewLifecycleOwner());
        }
        // [NOT OK] Would crash here before onAuthorized() — Room query hits locked DB
        currentLiveData = photoDao.getAllPhotosLive();
        currentLiveData.observe(getViewLifecycleOwner(), photos -> {
            adapter.submitList(photos);
        });
    }
}
```

**What CAN run in `onViewCreated()` pre-auth:**
- `findViewById()` / view binding
- `RecyclerView.setLayoutManager()`, `setAdapter()`
- Adapter constructor (as long as it does not touch the DB or filesystem)
- Tab layout setup, toolbar menu wiring, click listeners on static views
- Any UI operation that does not call into Room, `GDFileSystem`, `GDHttpClient`,
  or `com.good.gd.file.*`

**What MUST be deferred (inside the `getAuthorized().observe()` callback):**
- `AppDatabase.getInstance()` or any DAO access
- `LiveData.observe()` for Room DAO queries
- Any call to `SecureFileStore.openForRead/openForWrite`
- Any call to `GDFileSystem.*` or `com.good.gd.file.*`
- Any call to `GDHttpClient` or `BBCustomInterceptor`-backed OkHttp

**The `dependenciesInitialized` flag is required for three reasons:**

1. `getAuthorized()` LiveData may emit `true` more than once (e.g., after a
   lock/unlock cycle). Without the guard, `initDependencies()` runs multiple
   times, leaking database instances.
2. `onResume()` and `onHiddenChanged()` can fire before `onAuthorized()`.
   Without the guard they call `observePhotos()` which crashes because
   `photoDao` is still null.
3. Fragment recreation (e.g., rotation) calls `onViewCreated()` again. The
   flag ensures `initDependencies()` does not re-run if authorization already
   happened, avoiding a second `AppDatabase.getInstance()` call.

## Pattern 4: Guarding BroadcastReceivers and Services

### The Problem

BroadcastReceivers (e.g., alarm receivers, boot receivers) and Services
can be triggered by the system at any time — including before the user
has unlocked the Dynamics container. If they access secure APIs, they
crash.

### The Pattern

Use the static `isContainerAuthorized` flag as an early-exit guard:

```kotlin
class MyAlarmReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        // Guard: skip if Dynamics container is not authorized
        if (!MyApplication.isContainerAuthorized) {
            Log.w(TAG, "Container not authorized, skipping alarm")
            return
        }
        // Safe to access secure APIs
        val database = MyDatabase.getDatabase(context)
        // ... process alarm
    }
}
```

### Key Points

- BroadcastReceivers have no lifecycle, so LiveData observation is not
  appropriate. Use the static boolean.
- Silently skip the work rather than crashing. The work will be picked
  up when the user next opens the app and the container is authorized.
- Log a warning so developers can diagnose missed events during testing.

## Pattern 5: Guarding App Widgets

### The Problem

App widget factories (`RemoteViewsService.RemoteViewsFactory`) are
instantiated by the system and may run before authorization. Their `init`
blocks and `onDataSetChanged()` methods access the database.

### The Pattern

Defer database initialization in the widget factory using the same
LiveData observation pattern, with a static boolean fast-path:

```kotlin
class MyWidgetFactory(
    private val app: MyApplication,
    private val noteId: Long,
) : RemoteViewsService.RemoteViewsFactory {

    private lateinit var database: MyDatabase

    init {
        if (MyApplication.isContainerAuthorized) {
            database = MyDatabase.getDatabase(app)
        } else {
            app.authorized.observeForever(object : Observer<Boolean> {
                override fun onChanged(value: Boolean) {
                    if (value) {
                        app.authorized.removeObserver(this)
                        database = MyDatabase.getDatabase(app)
                    }
                }
            })
        }
    }

    override fun onDataSetChanged() {
        if (!::database.isInitialized) return  // Not yet authorized
        // Safe to query
    }
}
```

### Key Points

- Widget factories use `observeForever` because they have no lifecycle.
- Guard `onDataSetChanged()` against uninitialized database — the system
  can call it before the observer fires.
- Widget providers (`AppWidgetProvider.onUpdate()`) should also check
  `isContainerAuthorized` before accessing secure APIs.

## Pattern 6: Deferring Data Migrations and Schema Upgrades

### The Problem

Apps often run data migrations or schema upgrades on startup (e.g., in
`onCreate()` of the main Activity or Application class). These migrations
typically access the database and filesystem — both of which are inside
the Dynamics secure container.

### The Pattern

Wrap the migration call in an authorization observer:

```kotlin
private fun checkForMigrations() {
    if (needsMigration()) {
        val myApp = application as MyApplication
        myApp.authorized.observe(this) { authorized ->
            if (authorized) {
                lifecycleScope.launch {
                    runMigrations()
                    proceedWithNavigation()
                }
            }
        }
    } else {
        proceedWithNavigation()
    }
}
```

### Key Points

- Migrations that touch the database or filesystem MUST wait for
  authorization. This is easy to miss because migration code often
  predates the Dynamics integration and was never designed for deferred
  execution.
- If the migration shows a progress dialog, the dialog setup (UI-only)
  can happen before authorization, but the actual migration work must
  wait.
- Navigation that depends on migration completion should also be deferred.

## Pattern 7: Guarding Utility Functions That Access Secure Storage

### The Problem

Utility functions (e.g., `getPrivateStorageDirectory()`,
`ensureCacheDirectory()`) may be called during early initialization
before the container is authorized. If they use Dynamics file APIs
internally, they crash.

### The Pattern

Add a static boolean guard inside the utility function:

```kotlin
fun Context.getPrivateDataDirectory(): File {
    val path = "data/private"
    // Only create directory if container is authorized
    if (MyApplication.isContainerAuthorized) {
        GDFileHelper.ensureDirectory(path)
    }
    // Return the path reference regardless — callers that need
    // the directory to exist will only call after authorization
    return File(path)
}
```

### Key Points

- The function returns a `File` path reference even before authorization.
  This is safe because the `File` object is just a path wrapper — no I/O
  happens until someone reads/writes through it.
- The `ensureDirectory()` call (which does actual I/O) is guarded.
- Callers that do actual I/O through this path are themselves guarded by
  one of the patterns above.

### Common Consumers of Guarded Utility Functions

Adapter constructors in `onViewCreated()` frequently pass directory
paths as constructor arguments (e.g., `imageRoot`, `mediaDirectory`,
`thumbnailDir`). If the directory path is obtained via a GD file utility
function, the adapter constructor call must be deferred until
authorization. This is a frequent source of deterministic first-launch
crashes because:

1. The database deferral (Pattern 2/12) gives false confidence — "I
   deferred everything"
2. Computed properties (`val imageRoot get() = ...`) look like simple
   getters, obscuring the GD file constructor underneath
3. The crash is in a utility function 3+ levels deep from the Fragment,
   making the call chain non-obvious during a top-down audit

**Example (Fragment adapter receives a deferred secure path):**

```kotlin
// BEFORE — crashes: setupAdapter() called in onViewCreated() pre-auth.
// Call chain: onViewCreated() → setupAdapter() → model.imageRoot
//   → app.getCurrentImagesDirectory() → getPrivateAttachmentsRoot()
//   → GDFile("attachments") ← requires authorized container
private fun setupAdapter() {
    adapter = BaseNoteAdapter(
        ...,
        model.imageRoot,  // calls GDFile("attachments") internally
        ...
    )
}

// AFTER — defer adapter setup until authorization
private fun setupAdapter() {
    val gdApp = requireActivity().application as MyApplication
    if (gdApp.isContainerAuthorized) {
        createAdapter()
    } else {
        gdApp.authorized.observe(viewLifecycleOwner) { authorized ->
            if (authorized) createAdapter()
        }
    }
}

private fun createAdapter() {
    adapter = BaseNoteAdapter(
        ...,
        model.imageRoot,  // safe — container is now authorized
        ...
    )
    binding.recyclerView.adapter = adapter
}
```

**Alternative — guard the utility function itself (Pattern 7):**

```kotlin
// If the adapter is needed for layout measurement pre-auth, guard the
// utility function and provide a fallback path:
fun ContextWrapper.getPrivateAttachmentsRoot(): File {
    return if (MyApplication.isContainerAuthorized) {
        val root = GDFile("attachments")
        if (!root.exists()) root.mkdir()
        root
    } else {
        // Return a non-GD placeholder path; adapter won't load images
        // until post-auth refresh triggers
        File(filesDir, "attachments")
    }
}
```

**What to search for during audit (validator rule AUTH-FILE-001):**

```bash
# Find adapter setup methods in Fragment files
rg "setupAdapter|initAdapter|createAdapter" \
  -g "*Fragment.java" -g "*Fragment.kt" -n ${in_scope_main_src}

# For each hit, trace arguments back to GD file access
# Look for: model.<property>, viewModel.<property>, or direct
# utility calls that resolve to com.good.gd.file.File constructors
```

## Pattern 8: Null-Safety for Deferred Fields

### The Problem

When database-backed fields are deferred (Pattern 2), code that previously
used `!!` (non-null assertion) on those fields will throw
NullPointerException if called before initialization.

### The Pattern

Change non-null assertions to safe calls:

```kotlin
// [NOT OK] BEFORE — crashes if searchResults is null (not yet initialized)
var keyword = ""
    set(value) {
        field = value
        searchResults!!.fetch(keyword)
    }

// [OK] AFTER — safe call, silently skips if not yet initialized
var keyword = ""
    set(value) {
        field = value
        searchResults?.fetch(keyword)
    }
```

### Key Points

- Audit every `!!` assertion on fields that are initialized after
  authorization. Convert to `?.` safe calls.
- This is a common source of NullPointerException in migrated apps
  because the original code assumed fields were always initialized
  by the time they were accessed.

## Systematic Audit Checklist

After completing the import-swap migration, perform this audit to find
all pre-authorization secure API access.

> **Multi-module note**: every `rg ... app/src/main/java/` invocation
> below is a canonical-shape illustration. The operational scan target
> is `${in_scope_main_src}` — every `src/main/java` and `src/main/kotlin`
> directory across the primary application module **and** every entry
> in `libraryModulesInScope[]` from
> `dynamics-migration-tool/output/module-map.json`. Multi-module apps
> (especially large multi-feature repositories) routinely hide deferral hazards in
> feature/library modules, not the application module. See
> `04-multi-module-projects.md`.

### 1. Search for Database Access Points

```bash
rg "getDatabase|getWritableDatabase|getReadableDatabase|openOrCreateDatabase" \
  -g "*.java" -g "*.kt" -n app/src/main/java/
```

For each hit, verify it is either:
- Inside `onAuthorized()` or a method called from it
- Guarded by `isContainerAuthorized` check
- Deferred via LiveData observation on `authorized`
- In a secondary Activity (safe — user navigated there post-auth)
- In a user-triggered action (safe — UI is only interactive post-auth)

### 2. Search for File System Access Points

```bash
rg "GDFileSystem|GDFileHelper|com\.good\.gd\.file" \
  -g "*.java" -g "*.kt" -n app/src/main/java/
```

Apply the same verification as above.

### 3. Search for Network Access Points

```bash
rg "GDHttpClient|GDSocket|BBCustomInterceptor" \
  -g "*.java" -g "*.kt" -n app/src/main/java/
```

Apply the same verification as above.

### 4. Search for ViewModel init Blocks

```bash
rg "init \{" -g "*.kt" -n app/src/main/java/ | rg -i "model|viewmodel"
```

Verify no secure API access happens in `init {}` without authorization
deferral.

### 5. Search for BroadcastReceiver onReceive

```bash
rg "onReceive|BroadcastReceiver" -g "*.java" -g "*.kt" -n app/src/main/java/
```

Verify all receivers that access secure APIs have `isContainerAuthorized`
guards.

### 6. Search for Widget Factories

```bash
rg "RemoteViewsFactory|AppWidgetProvider" -g "*.java" -g "*.kt" -n app/src/main/java/
```

Verify widget code defers database access until authorized.

### 7. Search for Migration / Upgrade Code

```bash
rg "migration|upgrade|schema|runMigrations" -g "*.java" -g "*.kt" -n app/src/main/java/
```

Verify migration code that accesses the database or filesystem is
deferred until after authorization.

### 8. Search for Activity/Fragment Helper Methods That Access Secure APIs

```bash
rg "setupMenu|setupObserver|setupAdapter|initAdapter|createAdapter|checkForMigration|onResume|setupNavigation|setupDrawer|refreshData" \
  -g "*.java" -g "*.kt" -n app/src/main/java/
```

For each method in the main Activity or Fragment that accesses the
database, DAO, or GD file APIs (even indirectly through ViewModel
properties or computed property getters), verify it is gated behind
`databaseReady` or `authorized` LiveData.

**Special attention for adapter setup methods:** Trace every argument
passed to adapter constructors. If any argument resolves through a
ViewModel computed property or utility function to a
`com.good.gd.file.File` constructor, the adapter setup MUST be deferred
(see Pattern 7 — Common Consumers section).

### 9. Search for Application.ActivityLifecycleCallbacks

```bash
rg "ActivityLifecycleCallbacks|onActivityCreated|onActivityResumed" \
  -g "*.java" -g "*.kt" -n app/src/main/java/
```

Verify all lifecycle callback methods guard access to `lateinit`
properties with `::property.isInitialized` checks.

## Pattern 9: Deferring Activity Lifecycle Methods Beyond onCreate()

### The Problem

The main Activity's `onCreate()` is correctly deferred, but other methods
in the same Activity still access the database directly. Common examples:
- `setupMenu()` that populates a navigation drawer from DAO queries
- `onResume()` that refreshes a list from the database
- `checkForMigrations()` that runs schema upgrades
- `setupObservers()` that attaches LiveData observers backed by Room

### The Pattern

Gate each method behind the ViewModel's `databaseReady` signal:

```kotlin
private fun setupMenu() {
    baseModel.databaseReady.observe(this) { ready ->
        if (ready) populateMenuFromDatabase()
    }
}

private fun checkForMigrations() {
    baseModel.databaseReady.observe(this) { ready ->
        if (ready) runMigrations()
    }
}
```

### Key Points

- Audit EVERY method in the main Activity that accesses the database,
  not just `onCreate()` itself
- Methods called from `onResume()` are especially dangerous because
  `onResume()` fires on every Activity return, including the first one
  before authorization
- When heavy UI object fields (not just DB) are created only after
  authorization, also apply **Pattern 14** — null/ready guards on
  `onResume` / `onPause` / `onStop` / `onDestroy`

## Pattern 10: Guarding Application.ActivityLifecycleCallbacks

### The Problem

The Application class registers `ActivityLifecycleCallbacks` that access
`lateinit` properties (preferences, database handles, etc.) in callbacks
like `onActivityCreated()`. These callbacks fire for ALL Activities —
including the Dynamics SDK's internal Activities during activation/unlock,
which happen before `onAuthorized()` initializes the properties.

### The Pattern

Guard all property access with `::property.isInitialized`:

```kotlin
override fun onActivityCreated(activity: Activity, savedInstanceState: Bundle?) {
    if (!::preferences.isInitialized) return
    if (preferences.secureFlag.value) {
        activity.window.addFlags(WindowManager.LayoutParams.FLAG_SECURE)
    }
}
```

### Key Points

- The SDK's activation and lock screen Activities trigger these callbacks
  before the app's own `onAuthorized()` fires
- `lateinit` properties throw `UninitializedPropertyAccessException`, not
  `GDNotAuthorizedError` — this makes the crash less obviously related to
  Dynamics authorization timing
- Apply this guard to EVERY callback method

## Pattern 13: Deferring Secure Preferences / Theme / Settings on Launch

### The Problem

Migrating `SharedPreferences` to a Dynamics-backed helper
(`SecurePreferencesHelper` or equivalent using `com.good.gd.file.*`) is
necessary for container storage, but it converts every remaining launch-path
prefs call into secure file I/O. Apps commonly read prefs during Phase 1 to:

- Apply theme / night mode before `setContentView`
- Toggle `FLAG_SECURE` / screenshot blocking
- Load PIN, biometric, or unlock-gate material
- Read settings repositories from a shared base Activity

Those call sites compiled and ran fine against platform `SharedPreferences`.
After the swap they throw `GDNotAuthorizedError` on cold start — even when
Room/DB deferral and `activityInit()` are correct. Static Phase 4 may report
prefs storage as migrated while Phase 11 must still fail the launch path.

### The Pattern

Keep Phase 1 lifecycle methods side-effect free with respect to secure
prefs and GD file I/O. Apply shell UI only; defer prefs-backed work:

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    GDAndroid.getInstance().activityInit(this)
    setContentView(R.layout.activity_launch)
    // Do NOT read SecurePreferencesHelper / theme / PIN prefs here.
    MyApplication.runOnAuthorized {
        runOnUiThread {
            applyThemeFromSecurePrefs()
            applySecuritySettingsFromSecurePrefs()
            initializeUnlockUiFromSecurePrefs()
        }
    }
}
```

Safe alternatives when a value is required only after auth:

- Observe `authorized` / call `runOnAuthorized` before the first
  `getString` / `putString` on the secure prefs helper
- Guard utility functions with `isContainerAuthorized`
- Keep one-time legacy `SharedPreferences` → secure migration inside
  `onAuthorized()` only (see `42-secure-storage-sharedpreferences.md`)

### Key Points

- Mere construction of a prefs helper is often safe; **get/put methods**
  that open `com.good.gd.file.FileInputStream` / `FileOutputStream` are not
- Shared base Activities are part of the launch graph — audit them, not
  only the concrete launcher Activity
- Phase 11 enforces `[AUTH-PREF-001]` for Activity/Application
  `onCreate` / `onStart` / `onResume` reachability into GD file or
  secure-prefs I/O (including cross-class repository → helper chains)

## Pattern 14: Guarding Deferred Activity UI Fields Across Lifecycle

### The Problem

Two-phase Dynamics auth correctly moves heavy Activity setup into
`runOnAuthorized` → `initializeAuthorizedUi()` / `onDynamicsAuthorized()`
(camera preview, `NavController`, menus, adapters). Android still invokes
framework callbacks **before** that Phase-2 work finishes:

- `onResume()` / `onPause()` / `onStop()` / `onDestroy()` after the first
  `onCreate()`
- `onCreateOptionsMenu()` / `onPrepareOptionsMenu()` when Phase-1 calls
  `setSupportActionBar()` / Toolbar inflation

Unguarded code that touches deferred fields (`lateinit` navigation
controllers, preview objects, app interfaces) crashes with
`UninitializedPropertyAccessException` / `NullPointerException` even when
Phase 11 AUTH-PREF / AUTH-CTOR scans are green — the failure is a null UI
dependency, not a secure API call.

A related Phase-2 ordering bug: calling menu/setup helpers that
`observe()` LiveData/preferences which reach those controllers **before**
navigation is established causes the same crash when LiveData dispatches
the current value synchronously.

### The Pattern

1. Track readiness (`authorizedUiInitialized` or
   `::field.isInitialized` / null checks on deferred fields).
2. Make lifecycle **and menu** callbacks no-ops until ready.
3. In Phase-2, establish controllers/navigation **before** any
   LiveData/preference observe that uses those fields.
4. After Phase-2 wiring, call `invalidateOptionsMenu()` (and re-enter
   resume work if still visible) so the first no-op callbacks are
   recovered.

```java
private boolean authorizedUiInitialized = false;
private MyApplicationInterface applicationInterface;

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    GDAndroid.getInstance().activityInit(this);
    setContentView(R.layout.activity_main);
    setSupportActionBar(toolbar); // may trigger onCreateOptionsMenu immediately
    MyApplication.runOnAuthorized(() -> runOnUiThread(this::initializeAuthorizedUi));
}

private void initializeAuthorizedUi() {
    if (authorizedUiInitialized || isFinishing()) return;
    // Order matters: controllers before menu/LiveData observers.
    setupNavigation();
    setupMenu();
    applicationInterface = new MyApplicationInterface(...);
    authorizedUiInitialized = true;
    invalidateOptionsMenu();
    if (!isFinishing()) {
        resumeAfterAuthorization();
    }
}

@Override
public boolean onCreateOptionsMenu(Menu menu) {
    // [BB_DYNAMICS-MIGRATION] Pattern 14 — Toolbar may request the menu
    // during Phase 1 before setupNavigation() assigns navController.
    if (!authorizedUiInitialized) {
        return false;
    }
    getMenuInflater().inflate(R.menu.main, menu);
    return true;
}

@Override
protected void onResume() {
    super.onResume();
    if (!authorizedUiInitialized || applicationInterface == null) {
        return;
    }
    resumeAfterAuthorization();
}
```

Kotlin `lateinit` variant:

```kotlin
override fun onCreateOptionsMenu(menu: Menu): Boolean {
    // [BB_DYNAMICS-MIGRATION] Pattern 14
    if (!::navController.isInitialized) return false
    // ... inflate / wire menu using navController ...
    return true
}
```

### Key Points

- Guarding secure APIs with `isAuthorized` (steering/20) is necessary but
  **not sufficient** when object fields themselves are created post-auth
- Phase-1 may call `setSupportActionBar` — that alone can fire
  `onCreateOptionsMenu` before `onAuthorized`
- Do not use `?.` / silent skip as the only recovery path — after
  Phase-2 init, `invalidateOptionsMenu()` and re-enter resume work if
  the Activity is still visible
- Phase 11 enforces `[AUTH-UI-004]` when an Activity both defers UI init
  (`runOnAuthorized` / `initializeAuthorizedUi` / `setupNavigation` /
  `onDynamicsAuthorized`) and uses those deferred fields in lifecycle
  **or menu** methods without a ready/null/`isInitialized` guard

## Common Crash Signatures and Their Fixes

| Crash | Root Cause | Fix Pattern |
|-------|-----------|-------------|
| `GDNotAuthorizedError` in `onCreate()` | Database/file access before container unlock | Pattern 1 + 2: Defer via LiveData |
| `GDNotAuthorizedError` from secure prefs / theme / settings in launch Activity | SharedPreferences migrated to GD-backed helper but still read in Phase 1 | Pattern 13: Defer SecurePreferencesHelper get/put until `runOnAuthorized` |
| `NullPointerException` on ViewModel field | Field initialized after auth, accessed before | Pattern 3: Observe `databaseReady` |
| `GDNotAuthorizedError` in BroadcastReceiver | Alarm/system event before container unlock | Pattern 4: Static boolean guard |
| `GDNotAuthorizedError` in widget | System refreshes widget before auth | Pattern 5: Deferred widget init |
| `GDNotAuthorizedError` in migration code | Schema upgrade runs before auth | Pattern 6: Wrap in auth observer |
| `GDNotAuthorizedError` in utility function | Directory creation during early init | Pattern 7: Static boolean guard |
| `GDNotAuthorizedError` from adapter `setupAdapter()` via computed property | GD file path passed to adapter constructor in Fragment `onViewCreated()` | Pattern 7 guard on utility fn + Pattern 3 deferred adapter setup |
| `NullPointerException` on `!!` assertion | Deferred field accessed with non-null assert | Pattern 8: Convert to `?.`, or adopt Pattern 12 (non-null placeholder) |
| `GDNotAuthorizedError` in `setupMenu()` / `onResume()` | Activity helper methods access DB before auth | Pattern 9: Gate behind `databaseReady` |
| `UninitializedPropertyAccessException` in Application callbacks | `lateinit` accessed before `onAuthorized()` initializes it | Pattern 10: `::property.isInitialized` guard |
| `NullPointerException` in `onViewCreated` / `setupObserver` on `viewModel.X!!` | UI observed a nullable, delayed ViewModel field | Pattern 12: non-null placeholder + state machine |
| `GDNotAuthorizedError` from `RoomTrackingLiveData` on first render | Fragment attached to a DAO-backed `LiveData` exposed pre-auth | Pattern 12: forward DAO stream into a non-null placeholder after `databaseReady` |
| `NullPointerException` in `Activity.onResume` on deferred UI field (`applicationInterface`, preview, …) | Heavy UI constructed only in `initializeAuthorizedUi` / `runOnAuthorized`; first `onResume` runs pre-auth | Pattern 14: ready/null lifecycle guards + resume recovery after auth |
| `UninitializedPropertyAccessException` in `onCreateOptionsMenu` on deferred `lateinit` navigation/controller fields | Phase-1 `setSupportActionBar` requests menu before Phase-2 `setupNavigation()` | Pattern 14: `::field.isInitialized` / ready guard + `invalidateOptionsMenu()` after Phase-2 |
| `Unable to resume` / `UninitializedPropertyAccessException` from menu setup LiveData | Preference/list observes run before navigation/controllers are assigned | Pattern 14: establish navigation/controllers before LiveData observes that use them |

## Architecture Decision: LiveData vs. Callbacks vs. Coroutines

| Approach | Pros | Cons | Best For |
|----------|------|------|----------|
| LiveData observation | Lifecycle-aware, auto-cleanup, works with existing Android architecture | Requires lifecycle owner (not available in all contexts) | Activities, Fragments, ViewModels |
| Static boolean + callback | Simple, works everywhere | Single callback only, no lifecycle awareness | Application class, one-shot deferral |
| Static boolean guard | Simplest, synchronous | Does not defer — just skips | BroadcastReceivers, utility functions, widgets |
| Coroutine + suspendCancellableCoroutine | Integrates with coroutine-based code | More complex setup | Coroutine-heavy architectures |

For most migrations, the combination of LiveData (for reactive components)
and static boolean guards (for non-lifecycle components) covers all cases.

## Key Principle: The Authorization Boundary Is Not Just onCreate()

`20-auth-initialization.md` covers the main Activity's two-phase
initialization. This file extends that boundary to **every** component
that touches secure APIs before `onAuthorized()` — ViewModels, Fragments,
LiveData observers, widget factories, BroadcastReceivers, migration
routines, lazy singletons, and utility functions. The migration agent
must trace the full call graph from every secure API call back to its
trigger point and verify that the trigger cannot fire before
`onAuthorized()`.

## Pattern 11: Deferring WorkManager / JobScheduler / CoroutineWorker

Background workers that access secure APIs must guard on container authorization and skip/retry when unauthorized. This applies to `WorkManager`, `CoroutineWorker`, `JobScheduler`, and service-triggered background pipelines.

## Pattern 12: Non-Null Placeholder Observable + Startup State Machine

### The Problem

Patterns 2 and 3 defer database initialization (ViewModel `init {}`) and DAO
observer attachment (Fragment `onViewCreated`). That correctly moves the
secure work behind authorization, but the **UI surface** that observes those
fields still renders during Phase 1 — before authorization. If the
ViewModel exposes the DAO-backed stream directly (or holds a nullable
`LiveData<T>? = null`), the first-render path can either:

- crash with `NullPointerException` from `!!` on a delayed field (e.g.
  `model.notes!!`, `viewModel.items!!`, `binding.vm!!.data`), or
- crash by attaching an observer to a Room `LiveData` returned by the DAO
  before the secure container is authorized (`RoomTrackingLiveData` on
  `arch_disk_io` -> `GDNotAuthorizedError`).

Both are first-launch crashes that static "is this code post-auth?" checks
miss because the *observer* code itself looks innocuous — only the
*observable* it attaches to is delayed.

### The Pattern

Treat startup as an explicit 3-state machine and never let the UI observe
a `null` or DAO-backed value during Phase 1.

```
PRE_AUTH      -> placeholder observable only (loading/empty/default)
AUTH_READY    -> DB initialized, DAO stream attached, databaseReady=true
UI_ATTACHED   -> Fragment/UI observers bound to a NON-NULL observable
```

Rules the kit enforces (validator IDs in brackets):

- The ViewModel exposes UI-facing observables as **non-null** from the
  moment the ViewModel is created. Initialize them with a placeholder
  value, not `null`. [`AUTH-UI-002` warns when this is missing.]
- The ViewModel never re-assigns the public `LiveData` reference. The
  DAO-backed stream is forwarded into the placeholder via a `MediatorLiveData`
  / `addSource` / `combine` / `postValue`.
- Fragments and Activities **never** dereference delayed model fields with
  `!!` in startup paths (`onViewCreated`, `onCreateView`, `setupObserver`,
  `getObservable`). [`AUTH-UI-001` fails on this.]
- If database wiring is deferred behind a manual bootstrap method or custom
  placeholder wrapper, the startup state machine must still publish
  `databaseReady` and keep startup helpers off the model until the ready
  gate. [`AUTH-UI-003` fails on incomplete state machines.]
- The `databaseReady` signal (Pattern 2) is used to **enable interactive
  actions**, not to make UI observation safe — observation is always safe
  because the placeholder is non-null.

### Kotlin example (LiveData)

```kotlin
class NotesViewModel(app: Application) : AndroidViewModel(app) {

    // [BB_DYNAMICS-MIGRATION] Pattern 12 — non-null placeholder.
    // Always safe to observe, even before authorization.
    private val _notes = MediatorLiveData<List<Note>>().apply { value = emptyList() }
    val notes: LiveData<List<Note>> = _notes

    val databaseReady = MutableLiveData(false)

    init {
        val gdApp = app as MyApplication
        gdApp.authorized.observeForever(object : Observer<Boolean> {
            override fun onChanged(value: Boolean) {
                if (!value) return
                gdApp.authorized.removeObserver(this)
                val db = AppDatabase.getInstance(app)
                // Forward DAO LiveData into the placeholder. The public
                // `notes` reference does not change; observers stay valid.
                _notes.addSource(db.noteDao().getAllLive()) { rows ->
                    _notes.value = rows ?: emptyList()
                }
                databaseReady.postValue(true)
            }
        })
    }
}
```

### Kotlin example (StateFlow)

```kotlin
class NotesViewModel(app: Application) : AndroidViewModel(app) {
    private val _notes = MutableStateFlow<List<Note>>(emptyList())
    val notes: StateFlow<List<Note>> = _notes.asStateFlow()
    val databaseReady = MutableStateFlow(false)

    init {
        viewModelScope.launch {
            (app as MyApplication).authorizedFlow.first { it }
            val db = AppDatabase.getInstance(app)
            launch { db.noteDao().getAllFlow().collect { _notes.value = it } }
            databaseReady.value = true
        }
    }
}
```

### Fragment-side rule

```kotlin
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    // [BB_DYNAMICS-MIGRATION] Pattern 12 — never `!!` on delayed model fields.
    viewModel.notes.observe(viewLifecycleOwner) { render(it) }   // safe pre-auth (placeholder)
    viewModel.databaseReady.observe(viewLifecycleOwner) { ready ->
        if (ready) enableInteractiveActions()                    // gate writes/edits, not observation
    }
}
```

### What this pattern replaces

| Anti-pattern | Replacement |
|--------------|-------------|
| `var notes: LiveData<List<Note>>? = null` reassigned in `initDatabase()` | `MediatorLiveData` initialized with `emptyList()`, `addSource` after auth |
| `viewModel.notes!!.observe(...)` | `viewModel.notes.observe(...)` — non-null by construction |
| `if (vm.databaseReady.value == true) setupObserver()` gating observation | observation always safe; `databaseReady` gates interactive actions only |

### Abstract Fragment Template variant (very common)

Many apps use the **template-method pattern** for list screens — a base
`Fragment` implements `setupObserver()` once and calls into an abstract
hook that each subclass implements:

```kotlin
// BASE — the deferral marker (runOnAuthorized / authorized.observe) often
// lives elsewhere; the base class is usually unaware of the auth boundary.
abstract class BaseNotesFragment : Fragment() {
    internal val model: BaseNoteModel by activityViewModels()
    abstract fun getObservable(): LiveData<List<Item>>
    override fun onViewCreated(view: View, s: Bundle?) {
        super.onViewCreated(view, s)
        setupObserver()
    }
    private fun setupObserver() {
        getObservable().observe(viewLifecycleOwner) { /* render */ }
    }
}

// SUBCLASS — expression-bodied override of the template hook.
// This compiles and looks innocuous, but `baseNotes` is initialized
// from `runOnAuthorized {}` in the ViewModel and is `null` on first
// render. NPE in the subclass, on the line with `!!`.
class NotesFragment : BaseNotesFragment() {
    override fun getObservable() = model.baseNotes!!   // CRASH
}
```

**The fix is in the ViewModel, not the subclass.** Replace the nullable
delayed field with a non-null placeholder (`MediatorLiveData<List<Item>>`
or `MutableStateFlow<List<Item>>`) initialized to `emptyList()` /
`Loading` and forward the DAO/Room stream into it after authorization
(see the LiveData/StateFlow examples above). Every subclass override
then drops the `!!`:

```kotlin
class NotesFragment : BaseNotesFragment() {
    override fun getObservable() = model.baseNotes   // non-null by construction
}
```

The validator detects this anti-pattern via `[AUTH-UI-001]`:

- header-line `!!` on any `override fun` whose name appears in the
  startup-method list (`getObservable`, `setupObserver`, `observeData`,
  `subscribeUi`, etc.), and
- `!!` on `model.X` / `viewModel.X` inside any startup-scope block.

Note: subclass files of this shape usually contain **no** deferral
marker of their own. The validator therefore treats deferred-init as a
**project-wide** signal: any `runOnAuthorized` / `authorized.observe` /
`databaseReady` / `isContainerAuthorized` reference anywhere in the
in-scope source roots flips the Pattern 12 contract on for every file.

### Migration output / readme requirement

Prompt 03b requires the migration output to include an explicit
**Startup State Machine** note that names which ViewModels/Fragments
