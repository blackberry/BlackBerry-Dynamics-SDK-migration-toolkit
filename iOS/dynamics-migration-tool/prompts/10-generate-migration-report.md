# Task: Generate Migration Report

## Goal

Produce a machine-readable `migration-report.json` inside the
`dynamics-migration-tool/output/` directory that summarizes everything
the migration changed, what's covered, what still needs manual attention,
what isn't supported, and iOS-specific considerations.

**This prompt runs AFTER all other migration prompts (00pre, 00, 00b, 01-09, 09b, 11) are complete.**

**Prerequisite check**: Before starting, read `dynamics-migration-tool/output/bootstrap.json`
and confirm it exists. Copy its `runId` field — every report artifact you write must carry
the same `runId`. If `bootstrap.json` is missing, run prompt `00pre-bootstrap.md` first.

**Prompt gating**: When you have finished and the validation section below passes, you MUST
run the recorder:
```bash
bash ./dynamics-migration-tool/tooling/record-prompt-execution.sh \
  --prompt-id 10 \
  --status completed
```
The recorder will validate prerequisites (all prompts 00–09b and 11 completed, `.last-check.json`
present and passing) and refuse if gates are not satisfied.

## Steps

### 0. Load Analysis Artifact (Required)

Read `dynamics-migration-tool/output/migration-analysis.json` generated by
Prompt 00 and use it as the source artifact for:
- domain applicability/tier values
- unsupported feature candidates
- manual TODO candidate seeding

If this file is missing, stop and run Prompt 00 first.

Read `dynamics-migration-tool/output/auth-reachability.json` if present and
carry its evidence into `lifecycleSummary`. If missing, run prompt `03b`
scoped validation before report generation:

```bash
bash ./dynamics-migration-tool/tooling/validate.sh --check-prompt 03b
```

### 1. Inventory All Changes

Scan the project for every `[BB_DYNAMICS-MIGRATION]` comment:

```bash
rg "\[BB_DYNAMICS-MIGRATION\]" --include="*.swift" --include="*.m" --include="*.h" \
  --include="*.plist" --include="*.entitlements" --include="Podfile" -n
```

For each hit, record:
- File path (relative to project root)
- Whether the file was modified, created, or deleted
- One-line description of the change

### 2. Catalog API Replacements with Risk and Snippets

For each Dynamics API introduced, record:
- Category (networking, storage-file, storage-sql, storage-coredata, pasteboard, policy, webview, icc, auth, xcode-config)
- Original API
- Replacement API
- Files where the replacement was made
- Total occurrence count
- Risk level and reason:
  - low: drop-in replacement (e.g., `FileManager` → `GDFileManager`)
  - medium: API shape changes (e.g., `NSPersistentContainer` → custom stack)
  - high: behavioral change (e.g., path differences in secure container)
- Before/after code snippets (1-5 lines each, from actual codebase)

### 3. Assess Coverage

For each migration area, determine status:
- migrated: all instances replaced, no standard APIs remain for sensitive data
- partial: some instances replaced, some remain
- not-applicable: the app does not use this category

Areas to assess:
- Info.plist Dynamics configuration (GDApplicationID, GDApplicationVersion,
  `CFBundleURLTypes`, native-bundle `.sc2` / `.sc2.<version>` / `.sc3`, and
  discovery schemes)
- Secure networking (URLSession, Socket)
- Secure file storage (FileManager, FileHandle, streams)
- Secure SQL database (sqlite3)
- Secure Core Data (NSPersistentStoreCoordinator)
- Secure pasteboard (UIPasteboard DLP)
- Authorization and initialization
- Policy management
- WebView (WKWebView+GDNET)
- ICC / AppKinetics
- External data movement / DLP egress

For Tranche 3 storage closure, also populate a `storageClosure` block with:
- SQL wrapper status (`directSqlite`, `FMDB`, `GRDB`, `SQLite.swift`, `SQLCipher`)
- Core Data and SwiftData status (SwiftData must be explicit `migrated`/`blocked`/`not-applicable`)
- File writer + reader/follow-on closure status
- Sensitive UserDefaults, Keychain, and local-crypto decision status

For Tranche 4 networking/WebView closure, populate a `networkWebClosure` block with:
- URLSession call-site counts and post-auth timing state
- direct socket migrated/blocked counts
- custom protocol + pinning/trust decision status
- background-session classification and G12 dependency status
- WKWebView support/content/unsupported-feature closure status

For Tranche 5 DLP/ICC/policy closure, populate a `dlpIccPolicyClosure` **object**
(not a string / not a flat list) with nested evidence fields such as:
- `externalSurfacesByDirection` (or equivalent inventory)
- managed/unmanaged endpoint classification
- inbound secure-copy closure status
- outbound protected export approval/blocker status
- AppKinetics service/registration closure status
- residual URL/share payload path status
- policy API/timing/update/cache/default handling status

Use the exact key name `dlpIccPolicyClosure` required by schema 2.1.0 / Phase 12.
When DLP/ICC/policy domains are not-applicable, still include a minimal object
that records N/A with evidence rather than inventing alternate key names.

### 4. Collect Manual TODOs

List anything the agent could not automate:
- UEM entitlement configuration
- Runtime testing with UEM server
- Credential and activation testing
- Third-party library compatibility verification
- SwiftData factory verification (`GDSecureModelContainer.create`) if detected
- App Extension compatibility (if detected)
- Non-Dynamics build blockers (pre-existing API availability issues,
  deprecated APIs unrelated to migration)
- Any items flagged during earlier prompts

Assign priority: high (blocks production), medium (should do before release), low (nice to have).

**Build failure classification**: For any build failures recorded during
migration, clearly distinguish:
- **Migration-caused**: introduced by the tool's changes (must be resolved)
- **Pre-existing**: already present before migration according to developer attestation/history (report, don't block)
- **Unrelated**: environment-specific or transient issues

Include pre-existing blockers in `manualTodos` with `reason: "pre-existing"`.

### 5. Identify Unsupported Features

List any app features that are incompatible with Dynamics:

**Always check for and flag:**
- **Flutter hybrid** — `pubspec.yaml`, `GeneratedPluginRegistrant`,
  `FlutterEngine` / `FlutterViewController` / Flutter Runner (out of scope
  for this toolkit release; default `releaseReadiness` = `no-go`)
- **Share Extension** — `com.apple.share-services` / Share Extension targets
  (Dynamics-unsupported; isolate / non-shipping — see
  `17-app-extensions-and-share-extensions.md`)
- **Other App Extensions** — WidgetKit, SiriKit, Notification Service, etc.
- **SwiftData persistent history / same-store Core Data mixing** — only when
  those unsupported 15.1 limitations are present. Migrated `@Model` stores
  using `GDSecureModelContainer` are a coverage area, not an unsupported feature.
- **BitCode** — if was enabled (now disabled)
- **App Clips** — if App Clip target detected
- **CloudKit / iCloud** — if used for sensitive data
- **Certain WKWebView features** — WKDownload, WKFindConfiguration, etc.
- **Swift Concurrency Actors** — if actors init with secure storage access

**CRITICAL: Verify workarounds before listing.** Before adding a library
to `unsupportedFeatures`, search the codebase for existing workarounds.
Only genuinely unresolved incompatibilities belong in `unsupportedFeatures`.
Flutter has **no** Dynamics workaround in this toolkit release — always list
it when detected. Share Extensions likewise have **no** Dynamics-enable
path — always list when detected, and document isolate / redesign disposition.

### 6. Generate Runtime Test Plan

Create a test scenario for each migrated coverage area:
- Authorization flow test (activate, lock/unlock, wipe)
- One test per migrated area
- Policy retrieval test if policy was migrated
- Each scenario: name, steps, expected result, related areas

### 7. Build UEM Admin Handoff

Extract from Info.plist and migration context:
- `GDApplicationID` and `GDApplicationVersion`
- Primary `bundleIdentifier` (`CFBundleIdentifier` / PRODUCT_BUNDLE_IDENTIFIER
  for the primary migrated app target)
- If the workspace has **multiple application targets** (e.g. Swift + ObjC
  demos), also populate `additionalBundleIdentifiers` (array of the other
  app bundle IDs). Keep a single primary `bundleIdentifier` for Dynamics URL
  scheme derivation checks — do not invent a key named `urlSchemes`; the
  schema field is **`registeredUrlSchemes`**.
- mandatory Info.plist key status:
  - `GDApplicationID`
  - `GDApplicationVersion`
  - `CFBundleURLTypes`
  - `NSFaceIDUsageDescription`
  - `NSCameraUsageDescription`
  - `BlackBerryDynamics.CheckEventReceiver` (`present` for notification/GDState
    auth, `not-applicable` for `GDiOSDelegate` auth)
- registered Dynamics URL schemes (`registeredUrlSchemes` array):
  - `<primary-bundle-id>.sc2`
  - `<primary-bundle-id>.sc2.<GDApplicationVersion>`
  - `<primary-bundle-id>.sc3`
  - `com.good.gd.discovery`
  - setup-specific second discovery scheme (`com.good.gd.discovery.enterprise`
    for in-house/UEM-managed apps, none for partner/third-party apps,
    `com.good.gd.discovery.good` only for BlackBerry-developed apps)
- Step-by-step entitlement creation instructions for UEM
- Connectivity profile recommendations
- Compliance profile recommendations
- App permissions list

Also ensure `validationProof.phases` is copied from
`output/.last-check.json` `phasesExecuted` (non-empty array) and
`validation.warnings` / `validation.failures` are **integers** (not lists).

### 8. Run Validation and Record Results

Run a **full** validation sweep and capture:

```bash
bash ./dynamics-migration-tool/tooling/validate.sh
```

This writes `dynamics-migration-tool/output/.last-check.json`, which Prompt 10
completion requires. Prompt-scoped validation proof is rejected for Prompt 10.

Capture:
- Pass/fail status
- Failure count
- Warning count

**Warn vs pass for Prompt 10 recording:** full validate writes
`result=warn` when `failCount=0` but warnings remain. The recorder accepts
`pass` **or** `warn` when `failCount=0`. Still prefer clearing known noisy
warns when practical:
- `UserDefaults.standard.set(` — scoped to sensitive keys in app roots
- AppKinetics `GDServiceID` markers — skipped when all ICC sites are
  `removed` / `notApplicable`
- sqlite3enc expectation — skipped when `secureSql` is not-applicable

If `validate.sh` exits non-zero, fix the issues before proceeding to Step 9.
The report **must not be written** if full validation fails.
If `validate.sh` exits `3` (`ESCALATION REQUIRED`), stop broad reruns, inspect
`dynamics-migration-tool/output/migration-loop-state.json`, and repair the
owner prompt/domain indicated there before retrying.

### 9. Write the Report

Before writing `migration-report.json`, read:

- `dynamics-migration-tool/VERSION`

and include a required top-level `toolkit` block:

```json
"toolkit": {
  "name": "dynamics-migration-tool",
  "platform": "iOS",
  "version": "<value from VERSION file>",
  "reportSchemaVersion": "2.1.0"
}
```

Also include the run provenance block (values from `bootstrap.json`):

```json
"runProvenance": {
  "runId": "<bootstrap.json runId>",
  "bootstrapTimestamp": "<bootstrap.json timestamp>",
  "toolkitVersion": "<value from VERSION file>"
}
```

For schema 2.1.0 foundation closure, include these additional required
top-level blocks (do not infer them from prose):

- `targetMapSummary`
- `lifecycleSummary`
- `executedPromptAudit`
- `closureSummary`
- `blockers`
- `unresolvedCallSites`
- `validationProof`
- `apiCatalogEvidence`
- `runtimeEvidenceStatus`

When storage domains are applicable, include a `storageClosure` block that
summarizes Tranche 3 evidence (wrappers, SwiftData disposition, reader/writer
closure, and preferences/keychain/crypto decisions).

When networking/webview domains are applicable, include a `networkWebClosure`
block that summarizes G19/G20 evidence (timing, sockets, protocol/pinning,
background classification, and WKWebView closure state).

`lifecycleSummary` must include authorization-boundary evidence:
- selected authorization integration pattern
- post-auth boundary symbol/state signal
- window strategy and scene queueing strategy
- lifecycle root count, pre-auth risk count, opaque startup path count
- prompt `03` and `03b` scoped validation outcomes
- reachability analysis timestamp and source fingerprint

**IMPORTANT — File Write Method**: Use a **full-file overwrite** (not a
patch or append) to create both output files below. In AI IDEs, use the
Write/CreateFile tool — do NOT use StrReplace, ApplyPatch, or any
patch-based tool on JSON output files. Patch tools can append new content
to an existing file instead of replacing it, producing invalid JSON with
multiple root objects (e.g., `{new}{old}`). This causes `validate.sh` to
report "Extra data" and creates an unrecoverable loop.

**If the output file already exists** (from a previous run or failed
attempt): delete it first, then write the new file. If deletion is
blocked, truncate the file by writing the complete new content as a
full-file overwrite — this replaces the old content entirely.

Create `dynamics-migration-tool/output/` directory if needed, then generate
`migration-report.json` following:

- `steering/80-migration-report-schema.md` (schema keys/types)
- `steering/81-migration-report-contract.md` (quality gates)
- `steering/12-capability-and-support-model.md` (app complexity tiers, domain support levels, capability matrix)
- `steering/13-unsupported-feature-detection-matrix.md` (unsupported detection requirements)

When there is a conflict between code reality and `migration-analysis.json`,
prefer code reality and record the mismatch as a high-priority `manualTodo`.

## Critical Rules

- **ALWAYS use full-file overwrite** (Write/CreateFile tool) for JSON and markdown output — NEVER use patch-based tools (StrReplace, ApplyPatch) on output files
- **If validate.sh reports "Extra data"**: the output file contains multiple JSON objects from append corruption — delete the file and rewrite it completely using full-file overwrite
- The JSON must be valid, no comments, no trailing commas
- All file paths must be relative to the project root
- Output at `dynamics-migration-tool/output/migration-report.json`
- `schemaVersion` must be `"2.1.0"` — reports with `"2.0.0"` are **rejected** by the validator
- `platform` must be `"iOS"`
- Do NOT fabricate data — only report what actually changed
- Do NOT include `[BB_DYNAMICS-MIGRATION]` tags in the JSON
- `overallStatus` must accurately reflect the migration state
- `unsupportedFeatures` MUST include Flutter hybrid, Share
  Extension / App Extensions, and SwiftData **limitations** (persistent
  history, same-store mixing) if detected. Do not list ordinary SwiftData
  as unsupported after Prompt 04c migrates it.
- if Flutter hybrid is detected, `releaseReadiness.recommendation` MUST be
  `no-go` and the report MUST state that this toolkit release does not migrate
  Flutter apps (no official Dynamics Flutter SDK)
- if a Share Extension is detected:
  - list it in `unsupportedFeatures` (feature name containing
    `Share-Extension` or `Share Extension`)
  - `releaseReadiness.recommendation` MUST be `no-go` when the extension is
    still embedded in the Dynamics Archive, still bridges App Group sensitive
    data, or the product requires Share Extension with no approved redesign
  - `go-with-risks` is allowed only when the Share Extension is excluded from
    Dynamics shipping and residual risk is documented (see
    `17-app-extensions-and-share-extensions.md`)
- if storage domains are applicable, report must include explicit Tranche 3
  storage closure details (wrappers, SwiftData, readers/writers, prefs/keychain/crypto)
- if networking/webview domains are applicable, report must include explicit
  Tranche 4 `networkWebClosure` evidence
- if DLP/ICC/policy domains are applicable, report must include explicit
  Tranche 5 `dlpIccPolicyClosure` evidence
- `migration-analysis.json` must be consumed as report input (not ignored)
- before/after snippets must be real code from the project
- `runtimeTestPlan` must cover every migrated area
- If `dynamics-migration-tool/output/runtime-evidence.json` exists, treat it as
  the structured runtime-evidence source. Do not convert blocked or pending
  device/UEM/policy/human steps into success. Reflect `overallStatus: "passed"`
  as verified runtime evidence, `failed` as failed runtime evidence, and
  `blocked`/`pending`/`not-applicable` as unavailable or pending runtime
  verification with a concrete reason.
- When `secureSql` and/or `authorization` are applicable and
  `runtimeEvidenceStatus.runtimeVerification` is still `pending` /
  `unavailable`:
  - `releaseReadiness.recommendation` MUST NOT be `go`
  - use `go-with-risks` or `no-go`
  - document a **first Dynamics activate smoke** in
    `runtimeEvidenceStatus.notes` and/or `releaseReadiness.blockingItems`
    covering: post-auth root install (wire-before-attach / no IUO abort) and
    first `sqlite3enc` open+exec (no system-`libsqlite3` SIGSEGV)
  - prefer recording results into `output/runtime-evidence.json` tests
    `runtime-authorization-001` and `runtime-secure-sql-001`
- `uemAdminHandoff` must include `bundleIdentifier` (iOS-specific)
- `uemAdminHandoff` must include `requiredPlistKeys` with completed/missing
  status for `GDApplicationID`, `GDApplicationVersion`, `CFBundleURLTypes`,
  `NSFaceIDUsageDescription`, `NSCameraUsageDescription`, and conditional
  `BlackBerryDynamics.CheckEventReceiver`
- `uemAdminHandoff` and `Dynamics_Migration_Readme.md` must list the registered
  Dynamics URL schemes as completed migration requirements
- `Dynamics_Migration_Readme.md` must list the Face ID purpose string as a
  completed startup requirement
- toolkit.name/platform/version/reportSchemaVersion must be present and valid
- `migrationConfidence` must be present with score/level/rationale
- `releaseReadiness` must be present with go/go-with-risks/no-go recommendation
- report must contain explicit data-at-rest and data-in-transit security summaries
- `runProvenance.runId` must match `bootstrap.json` runId (recorder enforces this)
- Report is **not the final acceptance gate**: after this prompt succeeds, the developer
  must run the recorder (`record-prompt-execution.sh --prompt-id 10 --status completed`) to seal the migration state
- Do not silently skip the Prompt 12 handoff. Always ask the developer whether
  they want the optional migration retrospective after Prompt 10 is sealed.
